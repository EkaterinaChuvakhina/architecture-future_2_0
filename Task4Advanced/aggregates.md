# aggregates.md

**«Будущее 2.0» — Описание Aggregates**  
**Целевая событийная архитектура (DDD)**  
**Версия:** 1.0 (Горизонт 3 года)  
**Дата:** 14 апреля 2026

## 1. Управление пациентами

### 1.1. Профиль пациента — Root Aggregate
- **Границы**:  
  Включает: персональные данные, контакты, согласие (Consent), историю изменений профиля.  
  Не включает: медицинские записи, финансовые данные, записи на приём.
- **Инварианты**:
  - У пациента может быть только один активный профиль.
  - Все изменения профиля должны быть версионированы.
  - Согласие (Consent) обязательно должно быть явно получено перед передачей данных в другие домены.
- **Ключи**:`patientId`

### 1.2. Согласие 
- **Границы**:  
  Включает: тип согласия, дату выдачи/отзыва, область действия (данные для ИИ, финтех и т.д.).
- **Инварианты**:
  - Согласие не может быть отозвано задним числом.
  - При отзыве согласия все связанные данные в других доменах должны быть анонимизированы.
- **Ключи**: `consentId`, `patientId`

### 1.3. Запись на приём 
- **Границы**:  
  Включает: дату, время, врача, статус, пациента.
- **Инварианты**:
  - Нельзя создать запись на уже занятое время ресурса.
  - Запись может быть отменена только до начала приёма.
- **Ключи**: `appointmentId`, `patientId + slotTime`

## 2. Управление клиническими услугами

### 2.1. Электронная медицинская карта (EHR) — Root Aggregate
- **Границы**:  
  Включает: все записи по пациенту (осмотры, исследования, назначения).
- **Инварианты**:
  - EHR всегда должен быть в согласованном состоянии.
  - PHI-данные никогда не покидают этот агрегат без анонимизации.
- **Ключи**: `ehrId`, `patientId`

- **Границы**:
### 2.2. План лечения 
  Включает: цели лечения, этапы, сроки.
- **Инварианты**:
  - План не может быть закрыт, если есть невыполненные TreatmentOrder.
- **Ключи**: `carePlanId`, `ehrId`

### 2.3. Назначение лечения 
- **Границы**:  
  Включает: назначение, протокол, статус выполнения.
- **Инварианты**:
  - Назначение может быть выполнено только после подтверждения врачом.
- **Ключи**: `treatmentOrderId`, `ehrId`

## 3. ИИ-сервисы

### 3.1. Результат ИИ-диагностики  — Root Aggregate
- **Границы**:  
  Включает: входные данные (анонимизированные), модель, результат, confidence.
- **Инварианты**:
  - Результат всегда должен содержать объяснение (explainability).
- **Ключи**: `diagnosisRequestId`

### 3.2. Рекомендация 
- **Границы**:  
  Включает: текст рекомендации, уровень уверенности, связанные TreatmentOrder.
- **Инварианты**:
  - Рекомендация не может быть отправлена врачу без объяснения решения ИИ.
- **Ключи**: `recommendationId`

### 3.3. Модель ИИ 
- **Границы**:  
  Включает: версию модели, метрики, статус (active / training).
- **Инварианты**:
  - Только одна модель может быть active в production.
- **Ключи**: `modelId`, `version`

---

## 4. Финтех-сервисы

### 4.1. Банковский счёт  — Root Aggregate
- **Границы**:  
  Включает: баланс, историю транзакций, владельца (patientId).
- **Инварианты**:
  - Баланс не может стать отрицательным без овердрафта.
- **Ключи**: `accountId`, `patientId`

### 4.2. Кредит 
- **Границы**:  
  Включает: сумму, срок, статус, скоринг.
- **Инварианты**:
  - Кредит может быть выдан только при наличии активного согласия пациента.
- **Ключи**: `creditId`, `accountId`

### 4.3. Транзакция 
- **Границы**:  
  Включает: сумму, тип, статус.
- **Инварианты**:
  - Транзакция атомарна (все или ничего).
- **Ключи**: `transactionId`

---

## 5. Управление цепочками поставок

### 5.1. Элемент каталога препаратов
- **Границы**:  
  Включает: название, код МНН, остаток.
- **Инварианты**:
  - Остаток не может быть отрицательным.
- **Ключи**: `pharmaItemId`

### 5.2. Поставка / заказ — Root Aggregate
- **Границы**:  
  Включает: позиции, статус доставки, дату.
- **Инварианты**:
  - Заказ считается выполненным только после подтверждения IoT-телеметрии.
- **Ключи**: `supplyOrderId`

### 5.3. Данные телеметрии IoT 
- **Границы**:  
  Включает: показания оборудования, timestamp.
- **Инварианты**:
  - Телеметрия всегда должна быть связана с конкретным устройством.
- **Ключи**: `deviceId + timestamp`

---

## 6. Управление корпоративными операциями

### 6.1. Сотрудник
- **Границы**:  
  Включает: ФИО, должность, график.
- **Инварианты**:
  - График не может пересекаться с отпусками/отгулами.
- **Ключи**: `staffId`

### 6.2. Ресурс клиники и расписание — Root Aggregate
- **Границы**:  
  Включает: кабинет, оборудование, расписание.
- **Инварианты**:
  - Ресурс не может быть забронирован дважды на одно и то же время.
- **Ключи**: `resourceId`

---

## 7. Аналитика

### 7.1. Data Product — Root Aggregate
- **Границы**:  
  Включает: описание продукта, схему, уровень (Silver/Gold), владельца.
- **Инварианты**:
  - Data Product не может содержать PHI-данные.
- **Ключи**: `dataProductId`

### 7.2. Аналитическая витрина
- **Границы**:  
  Включает: materialized view, refresh policy.
- **Инварианты**:
  - Все данные должны быть анонимизированы на этапе ingestion.
- **Ключи**: `viewId`
